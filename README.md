# RSDGGS — Radio Spectrum Discrete Global Grid System

Rust reference implementation of the RSDGGS wire format, encoder, decoder, and ISM-band regulatory lookup database (sub-GHz and 2.4 GHz).

---

## Overview

RSDGGS is a hierarchical global grid that maps every point on a celestial body to a compact 1–8 octet binary index.  The grid is built on the dual of a regular icosahedron (a dodecahedral tiling of 12 pentagonal faces), with each face recursively subdivided into four triangular children at each resolution level.

This crate provides:

- **Encode** — convert (lat, lon, depth) → `RsdggsIndex`
- **Decode** — convert `RsdggsIndex` → geographic bounding cell and center
- **Wire I/O** — pack/unpack a 64-bit big-endian wire value
- **Regulatory lookup** — the band entries in force in a cell: its face's, or the exception overlay's where one applies
- **CBOR schema** — CDDL-driven minicbor serializers for all index and cell types
- **CLI test tool** — interactive encode/decode with regulatory and metro context output

## Wire Format

The RSDGGS wire value is a 64-bit big-endian unsigned integer packed MSB-first:

```
Bit  63–60   Body selector   (4 bits)  0x0=Earth, 0x1=Moon, 0x2=Mars
Bit  59–56   Face            (4 bits)  0–11
Bit  55–52   Triangle        (4 bits)  0–4; 5–15 reserved  (omitted at depth 1)
Bit  51– 0   Subdivision     (2 bits × up to 26 levels)
```

Every field ends on a nibble boundary: octet 1 holds the triangle and levels 1–2, and each later octet holds four levels.  Truncating an index to fewer octets is therefore just dropping trailing octets, and the hex form reads one field per digit after the face.

Octet depth (1–8) determines how many bits are significant.  Depth 1 encodes body+face only (continental resolution).  Depth 8 encodes all 26 subdivision levels (~centimeter resolution).

| Depth | Bits used | Approx. cell size |
|------:|----------:|------------------:|
|     1 |         8 | ~7 000 km (face)  |
|     2 |        16 | ~1 000 km         |
|     3 |        24 | ~65 km            |
|     4 |        32 | ~4 km             |
|     5 |        40 | ~260 m            |
|     6 |        48 | ~16 m             |
|     7 |        56 | ~1 m              |
|     8 |        64 | ~6 cm             |

Each octet after the first adds four levels, each halving the cell's edge, so a cell is about a sixteenth the size of its parent octet's (the draft's Table 5; checked with `examples/lookup` at 52°N 4°E).

## Coordinate System and Face Layout

The dodecahedron is oriented so that the most populous regulatory zones each sit on one face: **Face 1 is centred at 60.0°N 26.5°E** (Europe), and Face 2's centre lies at bearing 304.0° from it (North America). Weighted by city population, face 1 holds 99.6% of Europe, face 2 99.4% of the US, Canada and Mexico, and face 3 93% of the Region 3 core (China, India, Japan, Korea and their neighbours). The low two bits of a face number give the ITU Region of the face's main population (1, 2 or 3), or 0 for none.

| Face | Region label             | Approximate center     | Region (face & 3) |
|-----:|--------------------------|------------------------|-------------------|
|    0 | Antarctica / New Zealand | 60.0°S  153.5°W        | none              |
|    1 | Europe                   | 60.0°N   26.5°E        | 1                 |
|    2 | North America            | 39.6°N   79.3°W        | 2                 |
|    3 | Asia                     | 23.8°N  104.1°E        | 3                 |
|    4 | South Atlantic           | 54.8°S    1.2°E        | none              |
|    5 | Africa / Middle East     |  1.9°S   44.3°E        | 1                 |
|    6 | South America            | 23.8°S   75.9°W        | 2                 |
|    7 | Eastern Australia        |  6.4°S  161.3°E        | 3                 |
|    8 | Southern Indian Ocean    | 39.6°S  100.7°E        | none              |
|    9 | West Africa              |  6.4°N   18.7°W        | 1                 |
|   10 | Central Pacific          |  1.9°N  135.7°W        | 2                 |
|   11 | North Pacific            | 54.8°N  178.8°W        | 3                 |

Face centers and pentagon vertices are stored as f64 unit-vector triples in `src/constants.rs`, generated by `tools/gen_constants.py` from the orientation above (draft section 4.3).  They are derived analytically from the rotated icosahedron; no dataset is used at build time or runtime.

## CDDL Schemas and Code Generation

The two schemas in `cddl/` are compiled at build time by `cddlc` into minicbor
Rust serializers, which are then `include!()`'d into `src/cbor.rs`.

```
cddl/rsdggs.cddl     → $OUT_DIR/rsdggs_cbor.rs
cddl/regulatory.cddl → $OUT_DIR/regulatory_cbor.rs
```

`build.rs` invokes `cddlc` via the shell, strips inner `#![...]` crate attributes
from the output (they are invalid inside a module block), and writes the cleaned
file to `$OUT_DIR`.

**Known schema gap — `.size` range constraint:** The CDDL expression
`rsdggs-wire = bstr .size 1..8` is not yet supported by the cddlc parser
(`lower_size()` handles only exact integer sizes, not range operands).
As a workaround the schema declares `rsdggs-wire = bstr` with no size constraint;
the 1–8 octet range is enforced at runtime in `from_wire()`.

### Library (`[dependencies]`)

| Crate | Version | Purpose |
|-------|---------|---------|

### Test harness (`[dev-dependencies]`)

| Crate | Version | Purpose |
|-------|---------|---------|
| `approx` | 0.5 | `assert_abs_diff_eq!` macro for floating-point equality checks in `tests/roundtrip.rs`. |

### Build tool

| Tool | Source | Purpose |
|------|--------|---------|
| `cddlc` | [`dgtlrift/cddlc`](https://github.com/dgtlrift/cddlc) | CDDL compiler that generates Rust minicbor code from `.cddl` schemas at build time. |

`build.rs` uses, in order:
1. the binary the `CDDLC` environment variable names;
2. `cddlc` on the `PATH`;
3. the pinned release candidate, [`v1.1.0-rc.2`](https://github.com/dgtlrift/cddlc/releases/tag/v1.1.0-rc.2): a static x86-64 Linux binary that `build.rs` downloads with `curl` into `$OUT_DIR`, checks against its pinned SHA-256 with `sha256sum`, and unpacks with `tar`. On other hosts, install `cddlc` or set `CDDLC`.

The generated code is never checked in: the `.cddl` files are the source of truth, and what `cddlc` makes from them is an intermediate in `$OUT_DIR`.

The only network access is that download, at build time, when no `cddlc` is installed. At runtime there is none: all geographic constants, the regulatory database, and the metro reference data are embedded as static arrays.

## Regulatory Database

The regulatory database in `src/regulatory/earth.rs` (draft sections 8 and 9) has two parts:
- **face-level entries:** each face's dominant regime;
- **the exception overlay** (draft Table 7): locations the face-level entries get wrong, each with its own entries. A cell takes an exception's entries when, at the exception's resolution sufficiency level (RSL), its centre falls inside the exception's bounding box (and on its face and triangles, where given). The deepest RSL wins.

`regulatory::bands_for_index(&idx)` or `bands_for_location(lat, lon)` return the entries in force. An index shorter than an applicable exception's RSL is refused (`Error::InsufficientResolution`). An emission complies if it meets at least one entry that contains it.

## Known Implementation Gaps

### Moon and Mars (Body Selectors 0x1, 0x2)

The wire format reserves 4 bits for a celestial body selector.  Three bodies are
currently decoded: `Earth` (0x0), `Moon` (0x1), `Mars` (0x2).

**What works:** The `from_wire()` and `to_wire()` functions correctly decode the
body nibble for all three values.  Wire values with Moon or Mars body selectors
round-trip without error.

**What is not implemented:**

| Gap | Detail |
|-----|--------|
| **Selenographic coordinates** | The Moon uses a Mean Earth / Polar Axis (ME) principal axis reference frame (IAU WGCCRE).  No lunar face centers or pentagon vertices are defined.  `encode()` is Earth-only and returns `Error::NonEarthNotSupported` for other bodies. |
| **Areographic coordinates** | Mars uses the IAU Mars Mean Equator and IAU-node of epoch frame, with the prime meridian fixed by the Airy-0 crater.  Not implemented. |
| **Regulatory lookup** | `bands_for_face()` returns an empty iterator for non-Earth bodies.  No spectrum management frameworks exist for the Moon or Mars at present. |
| **Decode / bounding cell** | `decode()` uses Earth-centric face geometry.  Calling it on a Moon or Mars index produces a geographic coordinate that is meaningless but does not panic. |

**To add a body:** Define face centers and pentagon vertices for the body's
coordinate system in a new constants file, add a match arm in `encode()`,
and add a body-specific table in `src/regulatory/`.

### Additional Known Limitations

- **Face boundary points** fall into the nearest face by dot-product fallback.
  Points exactly on a face edge or vertex are assigned deterministically but the
  specific face is implementation-defined (not specified by the standard).
- **Cell area estimate** in the CLI tool uses a flat-earth approximation
  (`lat_span_km × lon_span_km`).  Actual spherical triangle areas differ slightly
  at high latitudes.
- **Metro context** uses centroid-distance heuristics (~280 cities) and an
  estimated urban radius of `√pop_M × 15 km`.  It is informational only and not
  part of the RSDGGS specification.
